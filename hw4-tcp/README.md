# Условие задания – вариант 36
Суда двух направлений проходят через одну или несколько шлюзовых камер. Каждая камера имеет ограниченную длину или вместимость, верхние и нижние ворота и управляемый уровень воды. Судно может войти только через открытые ворота при совпадающем уровне воды. 

Для пропуска группы судов диспетчер открывает ворота со стороны входа, выполняет загрузку камеры, закрывает ворота, изменяет уровень воды и открывает противоположные ворота. Одновременное открытие противоположных ворот запрещено. Суда другого направления ожидают освобождения и подготовки камеры.

Стратегия может формировать группы по направлению, размеру и
времени ожидания. Она не должна приводить к бесконечному ожиданию одного направления.

**Требуется разработать консольное приложение, моделирующее работу шлюзовой системы.**

## Входные параметры
- количество и вместимость камер;
- уровни участков канала;
- число, размеры и направления судов;
- интервалы прибытия;
- время открытия ворот и изменения уровня;
- стратегия формирования групп;
- правила приоритетного пропуска;
- максимальное время ожидания.

**Отображаемые события:** Программа отображает прибытие судна, постановку в очередь, подготовку камеры, открытие и закрытие ворот, вход, изменение уровня воды, выход, изменение направления работы и прохождение судном системы.

## Инварианты
- противоположные ворота одной камеры не открыты одновременно;
- уровень воды изменяется только при закрытых воротах;
- судно входит через сторону с совпадающим уровнем;
- вместимость камеры не превышается;
- судно не находится одновременно в двух камерах или участках.

## Завершение
Программа завершается после прохождения всех сформированных судов либо после окончания периода моделирования с выводом очередей, либо по прерыванию пользователем, если задан режим неограниченного по времени выполнения.

Диспетчер, камеры, ворота и каждое судно являются самостоятельными участниками модели.

# Представление сущностей клиентами и сервером
Я решил сделать диспетчера **сервером**, а остальные сущности (судна, камеры, ворота, а затем и мониторы) – **клиентами**.

Все клиенты циклически получают информацию от сервера и отправляют свою. На основе неё диспетчер отрабатывает взаимодействие клиентов и возвращает новые состояния. *Каждый клиент выводит и логирует только то, что у него в доступе, а сервер выводит все приходящие/уходящие запросы.*

В начале работы подключаются камеры, к ним по индексам – ворота. Если в этот момент в системе появится судно, оно будет ждать в очереди окончания конфигурации.

Судна могут прибывать (подключаться к серверу) когда угодно, на основе их нужд они будут обработаны. Такие клиенты могут прерываться, я отдельно учёл преждевременное отключение суден (судна Шрёдингера)

## Мониторы
Мониторы это отдельный тип клиентов (их может быть сколько угодно), которые могут подключаться и отключаться когда угодно, а во время работы они показывают работу всей шлюзовой системы. В начале работы сервер присылает ему снимок текущего состояния, а затем монитор ведёт собственную копию модели и по ней печатает журнал всей системы и итоговый отчёт.

# Запуск
Сборка сервера и четырёх клиентов в папку `bin/`:
```
make
```

## Запуск локально
Я написал скрипт для запуска всего сразу: сервера, монитора, камеры с воротами и суда. Адрес и порт обязательны, данные ставятся по умолчанию, лог сервера пишется в `locks.log`
```
./run.sh 127.0.0.1 6767
```

Запуск с данными из файла и записью в указанный лог
```
./run.sh 127.0.0.1 6767 tests/basic.txt basic.log
```

В терминале работает монитор: журнал всей системы, он ещё сохраняется в `basic_monitor.log`. Сервер пишет свой журнал только в `basic.log`, каждый клиент – в свой файл в папке `basic_clients/`. Суда запускаются по одному через случайные интервалы. Чтобы камеры и ворота подключились позже судов, есть `INFRA_DELAY=1 ./run.sh ...`.

## Ручной запуск и несколько компьютеров
Участников можно запускать вручную в отдельных терминалах или на разных компьютерах, в любом порядке. Клиенты указывают адрес машины с сервером.

Сервер (`0.0.0.0` – слушать все сетевые интерфейсы)
```
bin/server 0.0.0.0 6767 tests/basic.txt basic.log
```

Камера и её ворота (сторона: `0` – верхние, `1` – нижние). Каждый номер камеры и пара «камера + сторона» подключаются один раз
```
bin/chamber 192.168.1.10 6767 0
bin/gate 192.168.1.10 6767 0 0
bin/gate 192.168.1.10 6767 0 1
```

Судно: подключение = прибытие. Незаданные параметры выбираются случайно
```
bin/ship 192.168.1.10 6767
bin/ship 192.168.1.10 6767 --size 3 --dir backward --prio 1 --seed 42
```

Монитор: журнал всей системы. Мониторов может быть сколько угодно, подключаться можно в любой момент, лог необязателен
```
bin/monitor 192.168.1.10 6767 monitor.log
```

Шлюзование начинается, когда подключены все камеры и ворота. Суда, пришедшие раньше, ждут в очереди. Если в параметрах число судов равно `0`, суда принимаются без ограничения.

## Сигналы и завершение
Сигналы шлются серверу, например `kill -USR1 $(pgrep -x server)`:
- `SIGUSR1` – вывести состояние камер и очередей;
- `SIGUSR2` – включить или выключить ограничение по времени;
- `SIGINT` (Ctrl+C) и `SIGTERM` – корректно остановить модель.

При остановке сервер рассылает всем клиентам команду завершения, монитор печатает итоговый отчёт. Отключение судна или монитора (в том числе `kill -9`) на работу модели не влияет. Потеря камеры или ворот после начала шлюзования останавливает модель с выводом очередей. Общих ресурсов ОС нет, поэтому после аварийного завершения ничего удалять не нужно.
